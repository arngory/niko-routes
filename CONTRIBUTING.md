# Как вносить изменения

Коротко: короткая ветка от `main` → pull request → зелёные проверки → слияние (squash). Эти правила общие для
репозиториев Niko и узла (niko, raycontrol, niko-server, форки): везде тот же текст, кроме раздела «В этом
репозитории».

## Ветки и pull request

- `main` защищён: в него попадают только через pull request с зелёными проверками («Commit messages» и «Secrets»
  из `checks.yml`, плюс сборка репозитория, где она есть); без force-push и удаления. Обойти правило может только
  владелец.
- Задача — своя короткая ветка от свежего `main`: `<область>/<кратко>`, например `apps/ru-gosuslugi`,
  `ci/build-sets`, `docs/skeleton`. Ветка живёт дни, не недели; после слияния удаляется.
- Pull request открывается сразу, при необходимости черновиком (draft): проверки идут по нему, а не по push в ветку.
- Слияние — **squash**: заголовок и описание pull request становятся сообщением коммита в `main`, поэтому к ним те
  же требования, что к сообщению коммита (ниже). GitHub дописывает к заголовку « (#N)» — в окне слияния замените
  его на « (arngory/<репозиторий>#N)». Несколько независимых изменений — несколько pull request; rebase вместо
  squash — только если коммиты внутри осмысленны по отдельности.
- Сливает автор, когда проверки зелёные. Владелец видит каждый pull request и может остановить или откатить его.
- Шаблон описания — `.github/pull_request_template.md`: что и зачем, как проверено, что меняется для другой стороны.

## Сообщения коммитов

```
<что изменилось, по-английски, в настоящем времени, до 72 символов>

<зачем и как, строки до ~110 символов; спецификации по имени: rules-v1 §3, api-v1.md §2>
```

- **Без голых `#N`.** В форке GitHub связывает `#N` с issue родительского репозитория. Пишите полную форму
  `arngory/<репозиторий>#N` или «задача N». Проверяет «Commit messages» (`.github/scripts/bare-refs.py`) по
  коммитам, заголовку и описанию pull request, заново при каждой их правке.
- Закрывающие слова (`fixes`, `closes`) — только с полной формой и только там, где включены Issues.
- Без трейлеров `Co-Authored-By` и `Claude-Session` (решение владельца 2026-11-18): кто писал коммит, видно по его
  автору. В коммитах до этого дня они остаются.

## Секреты и данные

- Ключи, пароли, токены и адреса реальных узлов в репозиторий не попадают никогда. «Secrets» прогоняет gitleaks по
  коммитам pull request. Ложное срабатывание — в allowlist `.gitleaks.toml` (там пример) с комментарием, откуда
  ключ, отдельным pull request: проверка берёт `.gitleaks.toml` и `.gitleaksignore` из `main`, так что исключение
  действует со следующего pull request. Комментарии `gitleaks:allow` не учитываются.
- Скрипт «Commit messages», правила и исключения «Secrets» берутся из `main`, версия Go для gitleaks закреплена в
  `checks.yml`. Сами workflow идут в том виде, в каком лежат в pull request: pull request, который меняет
  `.github/workflows/`, меняет и свои проверки. Такой pull request другого участника сливает владелец.
- Секретные ключи — только в окружениях GitHub, не в секретах репозитория.
- Адреса в тестах и примерах — только документационные: `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`,
  `2001:db8::/32`, домены `*.example`, `*.test`.
- Приватные ссылки (сессии, холсты, рабочие пространства) в репозиторий не кладём.

## Закрепления

Всё, что берётся из другого репозитория, закреплено точной версией: коммит, тег, псевдоверсия Go или SHA-256 файла.
Закрепление меняется отдельным pull request с заголовком вида `Pin <что> <версия> (…)`: что, на что и зачем.
Закрепляем только тег или коммит постоянной ветки, не временную ветку: её могут удалить.

## В этом репозитории

Списки маршрутизации по приложениям для Niko (rules-v1): записи, из которых CI собирает подписанные наборы
sing-box. Формат, подпись и правила проверки — в [README](README.ru.md); замысел — в Niko,
[`docs/research/routing-apps.md`](https://github.com/arngory/niko/blob/main/docs/research/routing-apps.md).

| Что | Где |
|---|---|
| записи приложений и сервисов | `apps/<страна>/<id>.yaml` (пока нет) |
| открытые ключи: списков и свежести, эпоха 1 | `keys/lists.pub`, `keys/freshness.pub` |
| проверки pull request | `.github/workflows/checks.yml` |

- Записи — по одной на приложение или сервис, у каждой `evidence`. Каждое изменение — pull request, его смотрят
  два сопровождающих; записи `inside-only` — строже всего: они пускают трафик мимо зарубежного выхода.
- Pull request со стороны может менять только `apps/`. Остальное — workflow, ключи, скрипты, наборы стран,
  исключения — только сопровождающие.
- Сборку наборов и подпись запускает владелец: ключ списков — в окружении `lists-release` с ним как единственным
  проверяющим, ключ свежести — в `lists-freshness`. Выпуск — тег `m<эпоха>.<версия>`.
- Пока нет ни записей, ни сборки: формат обсуждается с клиентом Niko и узлом raycontrol.
