# niko-routes

[English](README.md) | Русский

Списки маршрутизации по приложениям для [Niko](https://github.com/arngory/niko). Каждая запись — приложение или
сервис: его пакеты, программы, домены и подсети. Из записей собираются подписанные наборы правил sing-box
(`.srs`).

**Статус: черновик.** Формат и схема подписи ниже — предложение, которое обсуждается с клиентом Niko и узлом
raycontrol. Пока ничего отсюда не используется. Замысел и доводы — в репозитории Niko,
[`docs/research/routing-apps.md`](https://github.com/arngory/niko/blob/main/docs/research/routing-apps.md).

## Почему приложения, а не домены

Маршрут одного сервиса по его доменам разрывает сервис: его собственные имена, CDN, аналитика и проверки адреса
никогда не укладываются в один список, часть уходит одним путём, часть другим, и сервис видит два адреса. Единица
маршрутизации здесь — приложение целиком (по пакету Android или программе Windows). Домены и подсети покрывают тот
же сервис, когда к нему ходит другое приложение, например браузер.

## Запись

Один файл на приложение или сервис, `apps/<страна>/<id>.yaml`:

```yaml
name: <отображаемое имя>
country: <ISO 3166-1 alpha-2, строчными>
kind: inside-only        # inside-only | blocked | ads
android:
  - package: <имя пакета>
    cert_sha256: [<SHA-256 сертификата подписи>]   # смена ключа APK v3: вся цепочка
windows: [<имя файла программы>]
domains: [<суффикс домена>]
asn: [<номер AS самого владельца сервиса>]
cidr: [<подсеть, если своей AS у владельца нет>]
cdn: [<CDN, на который опирается сервис, по имени>]
cname: [<разрешённые цели CNAME для имён записи>]
evidence: [<ссылка или запись трафика, где видны имена и адреса>]
```

- `inside-only` — работает только изнутри страны (проверяет страну адреса);
- `blocked` — заблокирован внутри страны;
- `ads` — реклама и трекеры.

## Что будет проверять CI

- схему; конфликты (одно имя или подсеть под двумя `kind`) и имена, общие для многих приложений;
- номера AS, развёрнутые в подсети по RouteViews (CC BY 4.0, с указанием источника);
- никаких подсетей CDN и общих облаков: адрес там обслуживает много сайтов, поэтому такие части сервиса
  сопоставляются только по имени;
- никакой подсети шире /16 для IPv4 и /32 для IPv6, никакой записи без `evidence`;
- `cname` перечисляет цели CNAME, на которые имена записи могут указывать вне её `domains`. Когда relay сам
  разрешает имя записи, каждая цель в цепочке CNAME должна быть под `domains` записи или совпадать с `cname`, иначе
  он отказывает; пустой `cname` не разрешает ни одного CNAME вне собственных доменов записи. CI держит `cname`
  узким (точные цели, а не вся зона провайдера, где имя может занять кто угодно) и отвергает цели, которые никуда
  не разрешаются или указывают на ресурс, который может занять кто угодно;
- имена сопоставляются по границам меток, строчными, только ASCII (IDN как A-метки), без точки в конце. Другой
  формы в наборах нет. sing-box сопоставляет `domain_suffix` без ведущей точки по границам меток и приводит хост к
  строчным, но точку в конце не убирает, поэтому клиент Niko убирает её в единственном месте, где его правила
  читают имя, откуда бы оно ни пришло (sniffing, входы SOCKS и HTTP);
- тег набора никогда не кончается на `.entries`, `.srs` или `.txt`;
- никаких суффиксов, поддомены которых третьи лица задают через DNS (общий хостинг, облачные зоны), и поиск висящих
  CNAME на ресурсы, которые может занять кто угодно: имена `inside-only` relay разрешает сам;
- запись, которая опирается на CDN, называет его (`cdn:`) из закрытого списка провайдеров, который ведёт CI, с
  `evidence` и ревью. Диапазоны этих провайдеров CI собирает в отдельные файлы (`cdn-<провайдер>`, `kind: cdn`,
  без `country`), перечисленные в подписанном манифесте, так что узел не может их подменить. Читает их только
  проверка relay над его собственным разрешением имён; наборы, nftables узла и правила клиента их пропускают, и это
  закреплено схемой манифеста. Запрета на подсети CDN в наборах это не снимает: relay выпускает разрешённый адрес в
  названный CDN, только если сам разрешил собственное имя этой записи;
- у каждого пакета Android есть сертификаты подписи (`cert_sha256`). Подтверждённый клиент помечает соединение
  набором, только если подпись установленного пакета совпадает: relay выпускает подтверждённое приложение
  `inside-only` на любой адрес, и приложение с чужим именем пакета метку получить не должно.

## Сборка и подпись

CI собирает по одному `.srs` на приложение и на каждую пару `kind` и страна, а также `manifest.json` с `epoch`,
версией, которая внутри эпохи только растёт (не больше 2^53), и для каждого файла — `name`, `sha256`, `size`,
`kind`, `country` и `form`. Эпоха должна совпадать с той, что встроена в читателя; выпуск, который выводит из
обращения утёкший ключ списков, поднимает её, и версия в новой эпохе начинается заново. Выпуск помечается тегом
`m<эпоха>.<версия>`, оба числа десятичные без ведущих нулей; тег, имя которого не совпадает байт в байт с именем в
его манифесте, ложный. Теги защищены от удаления и перезаписи, а читатель, который ищет на GitHub новейший выпуск,
смотрит только на теги своей эпохи.

- `kind`: `inside-only` | `blocked` | `ads` | `country` | `cdn`;
- `form`: `srs` (читает клиент) | `text` (читает сервер).

**Серверная форма наборов.** Рядом с каждым `.srs` CI собирает `<тег>.txt` из тех же записей YAML:

- строки `suffix:<домен>` и `cidr:<подсеть>`;
- домены строчными, IDN как A-метки (punycode), подсети в каноническом виде (`netip.Prefix.Masked`);
- по порядку, без повторов, UTF-8, LF, без комментариев.

Сервер читает только эту форму, клиент — только `.srs`. Обе получаются из одного коммита за один прогон CI, и обе
перечислены в манифесте.

**Наборы стран.** `country-<cc>.txt`, `kind: country`, только `form: text`, лишь строки `cidr:`, слитые и
свёрнутые:

- адрес попадает в набор страны, только если его относят туда **оба** источника: делегирования RIR
  (delegated-extended всех пяти RIR) **и** IPinfo Lite. Пересечение, а не объединение: чужой адрес, принятый за
  свой, открыл бы relay наружу, а обратная ошибка только отправляет соединение через узел;
- подсети CDN и облаков (те же исключения, что для записей), частные, служебные и bogon-диапазоны удаляются;
- IPinfo Lite распространяется под CC BY-SA 4.0, поэтому набор страны публикуется под CC BY-SA 4.0 с указанием
  IPinfo — здесь и в манифесте;
- если набор страны между версиями меняется больше чем на 5 % адресов, CI требует явной пометки человека с
  причиной в pull request, чтобы сломанный источник не прошёл незамеченным.

Relay выпускает наружу адреса назначения наборов `inside-only` своей страны и адреса из `country-<его cc>`.

Два ключа, как роли содержимого и метки времени в TUF:

- **ключ списков** подписывает `manifest.json` при выпуске, после принятых pull request, с одобрением задачи
  человеком. Его открытые ключи встроены только в клиент Niko и raycontrol и меняются только с их выпусками;
- **ключ свежести** каждый день подписывает небольшой `timestamp.json` (версия и SHA-256 манифеста, время подписи и
  `expires`, не позже чем через 14 дней) и кладёт его в незащищённую ветку `timestamp`. Ключ лежит в окружении
  GitHub, открытом только для ветки `main`, а не в секретах репозитория; сама задача требует
  `github.event_name == 'schedule'`, а в workflow нет триггеров `pull_request_target` и `workflow_dispatch`. Его
  открытые ключи перечислены в подписанном манифесте. Утечка этого ключа может лишь продлить жизнь старой версии,
  но не изменить списки.

У манифеста может быть несколько подписей, по одному `.minisig` на id ключа; читатель принимает его, если подпись
проверяет любой доверенный ключ списков. Читатель сначала проверяет манифест (ключ списков, его эпоху, версию не
ниже принятой им в этой эпохе), затем `timestamp.json` ключами свежести, которые перечисляет этот манифест.

## Участие

Правила репозиториев Niko — [CONTRIBUTING.md](CONTRIBUTING.md). Списки ведёт команда Niko, ключ списков держит
владелец. Pull request со стороны принимаются в таких пределах:

- pull request со стороны может трогать только записи в `apps/`; всё остальное (workflow, ключи, скрипты, наборы
  стран, исключения) CI отвергает, а `CODEOWNERS` отдаёт каждый другой путь сопровождающим;
- каждое изменение — pull request с `evidence`, его смотрят два сопровождающих;
- записи `inside-only` проверяются строже всего: они пускают трафик мимо зарубежного выхода, напрямую или через
  relay в стране пользователя;
- чужие списки можно брать как входные данные для CI, но не выпускать как есть.

## Ключи (владелец)

Текущие ключи, эпоха 1: ключ списков `352369B3BF839B6E` (`keys/lists.pub`), ключ свежести `062B6A45D2714A34`
(`keys/freshness.pub`).

- ключ списков: `minisign -G` на отключённой от сети машине; секретный ключ — в окружение `lists-release` как
  `LISTS_MINISIGN_KEY`, его пароль — как `LISTS_MINISIGN_PASSWORD`, владелец — единственный обязательный
  проверяющий; никогда не в секреты репозитория: их читает любой workflow репозитория, включая задачу свежести, и два
  ключа превратились бы в один. Окружение пускает только ветку `main`; сама задача подписи требует
  `github.ref == 'refs/heads/main'` и `github.event_name == 'workflow_dispatch'`, а в её workflow нет триггеров
  `pull_request` и `pull_request_target`. Запуск начинает и одобряет владелец («Prevent self-reviews» выключено,
  пока другого проверяющего нет). Открытый ключ — в `keys/lists.pub` здесь и в сборки Niko и raycontrol;
- ключ свежести: `minisign -G` так же; секретный ключ — в окружение `lists-freshness` как
  `FRESHNESS_MINISIGN_KEY`, его пароль — как `FRESHNESS_MINISIGN_PASSWORD`. У этого окружения нет проверяющих
  (задача идёт по расписанию каждый день), и оно пускает только `main`; открытый ключ — в `keys/freshness.pub`, и
  он перечислен в `manifest.json`.
